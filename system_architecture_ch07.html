7장. 분산 시스템에서 유일 ID 생성기 설계

DB 가 여러 곳인데 통틀어 유일한 ID 를 만들어야 한다. 방법은 여러 가지가 있다.
보충 표시는 공부 노트에 없던 내용을 보강한 부분이다.

1. 문제

  • DB 가 한 대면 auto_increment 로 충분하지만, 여러 대면 서버마다 번호를 따로 매겨 중복이 생긴다
  • 보충 책의 요구사항 : ID 는 유일 / 숫자로만 / 64비트 이내 / 발급 시각에 따라 정렬 가능 / 초당 10,000개 생성

2. 방법 4가지

2-1. 다중 마스터 복제 (multi-master replication)

  • DB 의 auto_increment 를 활용. 다음 ID 를 구할 때 1 이 아니라 k 만큼 증가. k = 사용 중인 DB 서버 수
중대한 단점
여러 데이터 센터에 걸쳐 규모를 늘리기 어렵다
ID 유일성은 보장되나 값이 시간 흐름에 맞춰 커지도록 보장되지 않는다
서버 추가/삭제 시에도 잘 동작하게 하기 어렵다

2-2. UUID

  • 유일성이 보장되는 ID 를 만드는 간단한 방법. 컴퓨터 시스템에 저장되는 정보를 유일하게 식별하기 위한 128비트 수
  • 예) 09c93e62-50b4-468d-bf8a-c07e1040bfb2
  • 충돌 가능성이 지극히 낮다 : 중복이 하나 생길 확률을 50% 로 올리려면 초당 10억 개를 100년간 만들어야 한다
장점단점
서버 사이 조율이 필요 없다 (서버마다 독립 생성)시간순 정렬 불가
규모 확장이 쉽다128비트로 길다 (요구는 64비트)
구현이 간단숫자 아닌 값(영문, 하이픈)이 포함

보충 최신 UUIDv7, ULID 는 앞부분에 시각을 넣어 시간순 정렬이 가능하다.

2-3. 티켓 서버 (ticket server)

  • Flickr 가 사용. 티켓 서버를 따로 두어 중앙집중형으로 하나만 사용 (auto_increment 를 쓰는 DB 한 대)
  • 👍 숫자로만 된 유일 ID 를 쉽게 만들 수 있고, 구현이 쉽다. 중소 규모 애플리케이션에 적합
  • 👎 티켓 서버가 SPOF. 장애가 나면 모든 시스템이 영향을 받는다
  • 보충 티켓 서버를 여러 대로 늘리면 서버 간 데이터 동기화 문제가 생긴다

2-4. 트위터 스노우플레이크 (snowflake) 기법

  • 생성할 ID 를 여러 구획으로 나눠서 만든다 (분할 정복)
구획크기설명
사인 비트1 비트항상 0. 나중을 위해 유보 (음수/양수 구분)
타임스탬프41 비트기원 시각(epoch) 이후 경과한 밀리초(ms)
데이터센터 ID5 비트25 = 32 개 데이터센터
서버 ID5 비트센터당 25 = 32 대
일련번호12 비트ID 를 만들 때마다 +1. 1ms 가 지나면 0 으로 리셋 → ms 당 212 = 4096 개
  • 보충 타임스탬프 41비트 = 241 ms ≈ 약 69년. 기원 시각은 보통 서비스 시작 시점 (트위터는 2010-11-04)
  • 보충 조립 : (타임스탬프 << 22) | (센터 << 17) | (서버 << 12) | 일련번호
  • 센터 ID 와 서버 ID 는 서버 시작 시 정해져 운영 중에는 바뀌지 않는다. 타임스탬프는 시간이 흐르며 커지고, 일련번호는 같은 ms 안에서만 증가한다
  • 👍 시간순 정렬, 64비트, 서버 간 조율 불필요, 대량 생성 가능

3. 설계 시 더 고려할 것 보충

  • 시계 동기화 : 서버마다 시각이 다르면 충돌 가능 → NTP 같은 네트워크 시간 프로토콜
  • 구획 길이 튜닝 : 동시성이 낮고 오래 쓰는 서비스면 일련번호를 줄이고 타임스탬프를 늘리는 식
  • 고가용성 : ID 생성기는 필수 시스템이라 아주 높은 가용성이 필요

복습 퀴즈 (눌러서 답 확인)

1. 여러 DB 에서 auto_increment 를 그대로 쓰면 안 되는 이유는?

서버마다 번호를 따로 매겨 서로 같은 ID 가 생긴다 (중복).

2. 다중 마스터 복제에서 k 는? 단점은?

k = DB 서버 수. 단점 : 여러 데이터 센터에 걸친 확장이 어렵고, 시간순이 보장되지 않고, 서버 추가/삭제가 어렵다.

3. UUID 의 장점과 단점은?

장점 : 서버 간 조율이 필요 없고 확장이 쉽다. 단점 : 시간순 정렬 불가, 128비트로 길다, 숫자만이 아니다.

4. 티켓 서버의 장점과 문제는?

숫자 ID 를 쉽게 만들고 구현이 쉽다. 하지만 SPOF 라서 장애 시 전체가 영향을 받는다.

5. 스노우플레이크의 구획과 비트 수는? 같은 ms 에 몇 개까지?

사인 1 + 타임스탬프 41 + 데이터센터 5 + 서버 5 + 일련번호 12 = 64비트. 일련번호 12비트이므로 서버 하나당 ms 당 4096개.

6. 스노우플레이크에서 시계 동기화가 중요한 이유는?

타임스탬프가 ID 의 앞쪽을 차지하므로, 서버 시각이 어긋나면 순서가 깨지거나 같은 ID 가 만들어질 수 있다. NTP 로 맞춘다.

더 공부할 거리 보충

  • UUID 버전(v1, v4, v7), ULID
  • NTP, 시계 오차 (clock drift)
  • 분산 DB 의 ID 전략 (MongoDB ObjectId 등)
