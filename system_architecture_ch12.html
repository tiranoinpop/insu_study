12장. 채팅 시스템 설계

4장 처리율 제한, 6장 키-값 저장소, 7장 유일 ID, 10장 푸시 알림이 함께 쓰인다.
보충 표시는 공부 노트에 없던 내용을 보강한 부분이다.

1. 요구사항 보충

  • 1:1 채팅, 소규모 그룹 채팅(최대 100명), 접속 상태 표시, 여러 단말 동시 접속, 푸시 알림
  • 규모 : DAU 5천만, 메시지 길이 10만 자 이하, 채팅 이력 영구 보관

2. 채팅 시스템의 기본 구조

클라이언트끼리 직접 통신하지 않는다. 모든 메시지는 채팅 서비스를 거친다.

채팅 서비스의 역할
클라이언트로부터 메시지를 수신
메시지 수신자를 결정하고 전달
수신자가 접속 상태가 아니면 접속할 때까지 메시지를 보관

3. 통신 프로토콜

메시지를 보낼 때 (발신 측)

  • HTTP 로도 충분. keep-alive 헤더로 연결을 유지 → TCP 핸드셰이크 횟수를 줄일 수 있다

메시지를 받을 때 (수신 측)

  • HTTP 는 클라이언트가 연결을 만드는 프로토콜이라서, 서버가 클라이언트에게 임의 시점에 메시지를 보내기 쉽지 않다
  • 해결책 3가지 : 폴링, 롱 폴링, 웹소켓
방식동작단점
폴링클라이언트가 주기적으로 새 메시지가 있는지 묻는다없을 때도 요청 → 서버 자원 낭비
롱 폴링물어본 뒤 서버가 새 메시지가 오거나 타임아웃될 때까지 연결 유지송수신자가 같은 서버에 안 붙을 수 있음, 연결 해제를 알기 어려움, 메시지가 없어도 주기적 재연결 보충
웹소켓HTTP 핸드셰이크(Upgrade) 후 양방향 영구 연결. 가장 널리 사용연결 유지 관리 필요 (상태 유지)
  • 웹소켓 : 서버가 비동기로 클라이언트에 메시지를 보낼 수 있다. 처음엔 HTTP 로 연결하지만 핸드셰이크 후 웹소켓으로 전환. 보충 80/443 포트를 써서 방화벽 문제가 적다
  • 메시지 양방향 전송 → 송신과 수신 모두 웹소켓으로 해도 된다

4. 개략적인 설계안

구분내용
무상태 서비스로그인, 회원가입, 프로필 등 전통적인 요청/응답. 로드 밸런서 뒤. 서비스 탐색(클라이언트가 접속할 채팅 서버 DNS 주소 목록 제공), 인증 서비스, 그룹 관리 등
상태 유지 서비스채팅 서비스. 클라이언트가 채팅 서버와 독립적인 네트워크 연결을 유지. 서버가 살아 있는 한 다른 서버로 연결을 바꾸지 않는다 (서비스 탐색이 장애를 감지하면 다른 서버를 안내)
제3자 서비스 연동푸시 알림 (10장). 앱이 꺼져 있어도 새 메시지를 알림

보충 동시 접속 100만 × 연결당 10KB ≈ 10GB → 서버 한 대로도 가능은 하지만 SPOF 라서 단일 서버 설계는 권장되지 않는다.

저장소

  • 적절한 DB 를 채택하는 게 중요. 데이터는 두 종류
    • 일반 데이터 (프로필, 설정, 친구 목록) : 안정성을 보장하는 관계형 DB, 다중화·샤딩
    • 채팅 이력 : 엄청난 양(페이스북·왓츠앱은 하루 수백억 건), 최근 메시지를 주로 조회, 검색·멘션·특정 메시지 점프 같은 무작위 접근
  • 키-값 저장소를 권장 : 수평적 규모 확장이 쉽고, 데이터 접근 지연 시간이 낮다 (관계형 DB 는 데이터가 크면 인덱스가 커져 롱테일 접근이 비효율적)
  • 사례 : 페이스북 메신저 - HBase, 디스코드 - Cassandra
데이터 모델 보충키
1:1 채팅 메시지PK message_id (message_from, message_to, content, created_at)
그룹 채팅 메시지복합 PK (channel_id, message_id). channel_id 가 샤딩 키

보충 message_id 는 고유하면서 정렬 가능(시간 순서 반영)해야 한다. created_at 은 같은 시각이 있을 수 있어 순서 기준으로 쓰면 안 된다 → 7장 스노우플레이크 또는 채널 안에서만 유일하면 되는 지역 순서 번호 생성기.
서비스 탐색은 지리적 위치, 서버 용량 등을 고려해 최적의 채팅 서버를 추천한다 (예: Apache ZooKeeper).

5. 메시지 흐름

1:1 채팅

  1. 사용자 A 가 채팅 서버 1 로 메시지 전송
  2. 서버 1 이 ID 생성기로 메시지 ID 결정
  3. 메시지를 메시지 동기화 큐로 전송
  4. 메시지를 키-값 저장소에 보관
  5. 사용자 B 가 접속 중이면 메시지를 채팅 서버 2 로 전달 → 서버 2 가 B 에게 전송
  6. 접속 중이 아니면 푸시 알림 메시지를 푸시 알림 서버로 보낸다

여러 단말 사이 메시지 동기화

  • 예) 폰에서 하던 대화를 PC 카톡에서 이어서
  • 같은 사용자는 같은 채팅 서버에 연결
  • 각 단말은 가장 최신 메시지 ID(cur_max_message_id)를 추적
  • 최신 메시지 ID 까지 동기화 작업을 수행 : 수신자가 현재 사용자이고, 저장된 메시지 ID 가 cur_max_message_id 보다 큰 메시지를 가져온다 보충

소규모 그룹 채팅

  • 각 수신자의 메시지 동기화 큐에 메시지를 각각 넣는 방법 (WeChat)
  • 👍 그룹이 작으면 메시지 동기화 흐름이 단순하고, 수신 측은 자기 큐만 확인하면 된다
  • 👎 그룹이 커지면 수신자마다 복사하는 비용이 커진다 → 그룹 크기를 제한해야 한다 (WeChat 은 500명)

6. 접속 상태 표시

  • 접속 상태 서버가 사용자 상태를 관리 (웹소켓으로 통신하는 실시간 서비스의 일부)
  • 로그인 : 웹소켓 연결을 맺은 뒤 접속 상태 서버가 상태(online)와 last_active_at 타임스탬프를 키-값 저장소에 보관 → 이후 접속 중으로 표시
  • 로그아웃 : 같은 방식으로 오프라인으로 바꾼다
  • 접속 장애 : 잠깐 끊어졌다고 매번 상태를 바꾸면 과하고 사용자 경험도 나쁘다
  • 박동(heartbeat) 이벤트 : 온라인 클라이언트가 n초 간격으로 서버에 박동 신호를 보낸다. 일정 시간(x초) 안에 박동을 받으면 온라인, 못 받으면 오프라인으로 간주
  • 보충 상태 변화 전파 : 발행-구독(pub/sub) 모델. 친구마다 채널을 두고 상태가 바뀌면 그 채널로 이벤트를 발행, 친구는 자기 채널을 구독. 그룹이 크면 전체에 전파하지 않고 그룹 입장 시나 친구 목록 갱신 시에만 상태를 가져온다

7. 추가 논의 보충

  • 미디어 파일(사진, 비디오) 지원 : 압축, 클라우드 저장소, 썸네일
  • 종단간 암호화 (E2E)
  • 캐시, 로딩 속도 개선 (지리적으로 분산된 네트워크, 예: Slack)
  • 오류 처리 : 채팅 서버가 죽으면 서비스 탐색(ZooKeeper)이 새 서버를 안내. 메시지 재전송 메커니즘(재시도, 큐)

복습 퀴즈 (눌러서 답 확인)

1. 클라이언트끼리 직접 통신하지 않는 이유와 채팅 서비스의 3가지 역할은?

수신자를 결정하고 오프라인 메시지를 보관해야 하므로 중간에 채팅 서비스가 필요. 역할 : 메시지 수신, 수신자 결정과 전달, 오프라인이면 접속할 때까지 보관.

2. 폴링, 롱 폴링, 웹소켓의 차이와 웹소켓이 널리 쓰이는 이유는?

폴링은 주기적으로 물어서 낭비, 롱 폴링은 메시지가 올 때까지 연결을 유지하지만 비효율이 남는다. 웹소켓은 HTTP 핸드셰이크 후 양방향 영구 연결이라 서버가 바로 보낼 수 있고 80/443 포트라 방화벽 문제도 적다.

3. 무상태 서비스와 상태 유지 서비스에는 무엇이 있나?

무상태 : 로그인·가입·프로필, 서비스 탐색, 인증, 그룹 관리. 상태 유지 : 채팅 서비스(웹소켓 연결 유지).

4. 채팅 이력 저장에 키-값 저장소를 쓰는 이유는?

수평 확장이 쉽고 지연 시간이 낮으며, 방대한 이력의 무작위 접근에서 관계형 DB 보다 유리하다. (페이스북 HBase, 디스코드 Cassandra)

5. message_id 를 created_at 이 아니라 ID 로 정렬하는 이유는?

같은 시각에 만든 메시지가 있을 수 있어 순서가 모호하다. 정렬 가능한 고유 ID(스노우플레이크 등)로 순서를 정한다.

6. 1:1 메시지 흐름 6단계는?

A → 채팅 서버 1 → ID 생성 → 메시지 동기화 큐 → 키-값 저장소 저장 → B 가 접속 중이면 채팅 서버 2 로 전달, 아니면 푸시 알림 서버로.

7. 박동(heartbeat)은 왜 필요한가?

잠깐 연결이 끊길 때마다 오프라인으로 바꾸면 사용자 경험이 나쁘다. n초마다 박동을 보내고 일정 시간 못 받았을 때만 오프라인으로 판단한다.

더 공부할 거리 보충

  • WebSocket 프로토콜, STOMP, Socket.IO
  • Apache ZooKeeper
  • 발행-구독 (Redis Pub/Sub, Kafka)
  • 종단간 암호화 (Signal 프로토콜)
