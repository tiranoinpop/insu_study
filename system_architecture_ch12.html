12장. 유튜브 설계

동영상을 올리고 스트리밍하는 서비스. 핵심은 비디오 트랜스코딩과 CDN.
보충 표시는 공부 노트에 없던 내용을 보강한 부분이다.

1. 요구사항 보충

  • 빠른 비디오 업로드, 부드러운 재생, 재생 품질 선택, 낮은 인프라 비용
  • 높은 가용성, 규모 확장성, 안정성
  • 모바일 앱, 웹 브라우저, 스마트 TV 지원
  • 책의 가정 : DAU 500만 / 하루 평균 5개 영상 시청 / 10% 가 업로드 (평균 300MB) → 매일 150TB 저장소 필요

저장소와 CDN 은 직접 만들지 않고 클라우드 서비스(S3, CloudFront 등)를 쓰는 것이 현실적이다. 바퀴를 새로 만들지 않는다.

2. 개략적 설계안

컴포넌트하는 일
클라이언트컴퓨터, 모바일 폰, 스마트 TV 에서 유튜브를 본다
CDN비디오를 저장하고 스트리밍한다 (1장 CDN)
API 서버비디오 스트리밍을 제외한 모든 요청 : 피드 추천, 업로드 URL 생성, 메타데이터 DB·캐시 갱신, 회원가입 등

비디오 업로드 절차

컴포넌트하는 일
사용자업로드하는 주체
로드 밸런서API 서버로 요청을 분산
API 서버업로드 요청 처리, 메타데이터 갱신
메타데이터 데이터베이스 / 캐시비디오 정보(파일 이름, 크기, 포맷, 소유자, 설명 등)
원본 저장소
(Blob Storage)		사용자가 올린 원본 비디오를 보관 (Binary Large OBject)
트랜스코딩 서버비디오를 여러 포맷으로 변환
트랜스코딩 비디오 저장소변환이 끝난 비디오
  1. 비디오를 원본 저장소에 업로드
  2. 트랜스코딩 서버가 원본을 가져와 여러 포맷으로 변환
  3. 변환이 끝나면 동시에(병렬) 두 가지 진행
    • (a) 변환된 비디오를 트랜스코딩 비디오 저장소에 저장 → CDN 으로 배포
    • (b) 완료 이벤트를 완료 큐에 넣고 완료 핸들러가 메타데이터 DB·캐시를 갱신
  4. API 서버가 클라이언트에게 업로드가 끝났음을 알린다

보충 비디오 업로드와 메타데이터 갱신(파일 이름, 크기, 포맷 등)은 병렬로 진행한다.

비디오 스트리밍

  • 스트리밍 : 내려받는 즉시 소량씩 지속적으로 받아 재생한다 (다 받은 뒤 재생하는 다운로드와 다르다)
  • 보충 프로토콜 : MPEG-DASH, Apple HLS, Microsoft Smooth Streaming, Adobe HDS. 프로토콜마다 지원하는 비디오 인코딩과 플레이어가 다르므로 서비스에 맞는 것을 고른다
  • 비디오는 가장 가까운 CDN 엣지 서버에서 전달해 지연을 줄인다

3. 비디오 트랜스코딩

트랜스코딩(인코딩) : 원본 비디오를 다른 포맷·해상도·비트레이트로 변환하는 일. 원본 비디오는 용량이 매우 크고, 기기마다 지원 포맷이 다르기 때문에 꼭 필요하다.

왜 하나설명
저장 공간 최적화원본은 비트레이트가 높아 저장 공간을 많이 차지 (1시간짜리 HD 가 수백 MB ~ 수 GB). 압축해서 줄인다
다양한 비디오 포맷 지원단말·브라우저마다 지원 포맷이 다름 → 여러 포맷으로 인코딩해 둔다
다양한 네트워크 대역폭에 대응고화질은 대역폭이 충분한 사용자에게, 저화질은 느린 사용자에게. 네트워크가 바뀌면 화질을 자동 전환

보충 컨테이너 : 비디오·오디오·메타데이터를 담는 바구니 (.avi, .mov, .mp4). 코덱 : 비디오를 압축·해제하는 알고리즘 (H.264, VP9, HEVC).

유향 비순환 그래프(DAG) 모델

  • 제작자마다 요구하는 처리가 다르다 (썸네일, 워터마크, 화질 등). 이를 유연하게 지원하고 병렬로 처리하려고 쓰는 모델
  • 작업을 단계별로 배열해서 순차적으로 또는 병렬적으로 실행될 수 있게 한다 (유향 = 방향 있음, 비순환 = 돌아오지 않음)
  • 예) 원본을 비디오 / 오디오 / 메타데이터 로 나눈 뒤, 각각 작업을 하고 마지막에 합친다

비디오 트랜스코딩 아키텍처

컴포넌트하는 일
전처리기 비디오 분할 : 비디오를 GOP(Group Of Pictures, 독립적으로 재생 가능한 프레임 묶음. 보통 수 초) 단위로 나눈다.
DAG 생성 : 프로그래머가 정의한 설정 파일에 따라 DAG 를 만든다.
데이터 캐시 : 분할된 GOP·메타데이터를 임시 저장 (실패했을 때 재시도에 활용)
DAG 스케줄러DAG 를 단계별 작업으로 쪼개 자원 관리자의 작업 큐에 넣는다
자원 관리자최적의 작업/서버 조합을 골라, 해당 작업 서버가 작업을 수행하도록 지시 (작업 큐 · 작업 서버 큐 · 실행 큐 + 작업 스케줄러)
작업 실행 서버DAG 에 정의된 작업(인코딩, 썸네일, 워터마크) 을 수행
임시 저장소 보충메타데이터는 메모리, 비디오·오디오 데이터는 Blob 저장소에 보관. 작업이 끝나면 지운다
인코딩된 비디오최종 결과물 (예 : funny_720p.mp4)

4. 시스템 최적화

속도 최적화

  • 느슨하게 결합된 시스템을 만들어 병렬성을 높인다
  • 결합도를 낮추려고 컴포넌트 사이에 메시지 큐를 둔다 (1장 메시지 큐) : 한 모듈이 느려도 다른 모듈이 기다리지 않고 병렬로 일한다
  • 보충 비디오를 GOP 단위로 쪼개 병렬 업로드하면 일부가 실패해도 그 조각만 재시도할 수 있다
  • 보충 업로드 센터를 사용자 가까이 둔다 (지리적으로 분산된 CDN 을 업로드 센터로 활용)

비용 최적화

  • CDN 은 비싸다 (전송량 과금). 비디오 인기도는 롱테일이라 소수의 인기 비디오가 조회의 대부분을 차지한다
  • 인기 비디오는 CDN 을 통해 재생하고, 다른 비디오는 비디오 서버를 통해 재생한다
  • 보충 인기 없는 비디오는 필요할 때만 인코딩하고, 짧은 비디오는 재생 시점에 인코딩. 지역별 인기에 따라 일부 지역에만 CDN 배포. 자체 CDN 을 만들어 ISP 와 제휴 (넷플릭스)

안전 최적화 보충

방법설명
미리 사인된 업로드 URL
(pre-signed URL)		인증된 사용자만 정해진 URL 로 업로드할 수 있게 한다
저작권 보호DRM, AES 암호화, 비주얼 워터마크

오류 처리 보충

종류대응
복구 가능한 오류예) 트랜스코딩 실패 → 재시도
복구 불가능한 오류예) 비디오 포맷이 잘못됨 → 오류 코드를 반환
API 서버 장애무상태라 다른 서버로 요청을 보낸다
메타데이터 캐시 / DB 장애캐시는 다중화, DB 는 주가 죽으면 부를 주로 승격 (1장 다중화)
작업 서버 / 스케줄러 / 큐 장애다른 서버에서 작업을 재시도, 자원 관리자 큐는 복제본 사용

복습 퀴즈 (눌러서 답 확인)

1. 업로드 절차를 순서대로 말해 보자

사용자 → 로드 밸런서 → API 서버(메타데이터 DB·캐시 갱신), 원본을 원본 저장소에 업로드 → 트랜스코딩 서버가 변환 → 변환본을 트랜스코딩 저장소(→ CDN)에 저장, 완료 이벤트로 메타데이터 갱신.

2. 트랜스코딩이 필요한 이유 3가지는?

저장 공간 최적화, 다양한 포맷 지원, 다양한 네트워크 대역폭에 맞는 화질 제공.

3. DAG 모델을 쓰는 이유는?

제작자마다 처리 요구가 달라 작업을 유연하게 정의하고, 작업을 단계별로 배열해 순차 또는 병렬로 실행하기 위해서.

4. 트랜스코딩 아키텍처의 컴포넌트는?

전처리기(GOP 분할, DAG 생성, 데이터 캐시) → DAG 스케줄러 → 자원 관리자(최적의 작업/서버 조합 선택) → 작업 실행 서버 → 인코딩된 비디오.

5. 속도를 높이는 방법은?

컴포넌트 사이에 메시지 큐를 두어 결합도를 낮춰 병렬성을 높인다. 비디오를 GOP 로 쪼개 병렬 업로드·처리.

6. CDN 비용은 어떻게 줄이나?

인기 비디오만 CDN 으로 재생하고, 나머지는 비디오 서버에서 재생한다 (롱테일).

더 공부할 거리 보충

  • HLS / MPEG-DASH, 적응형 비트레이트 스트리밍(ABR)
  • H.264, VP9, AV1 코덱
  • FFmpeg 로 직접 트랜스코딩 해 보기
