9장. 웹 크롤러 설계

Web Crawler (robot, spider). 웹에 새로 올라오거나 갱신된 콘텐츠를 찾아내는 기술.
보충 표시는 공부 노트에 없던 내용을 보강한 부분이다.

1. 웹 크롤러란

  • 검색 엔진에서 널리 쓰는 기술. 웹에 새로 올라오거나 갱신된 콘텐츠를 찾아내는 것이 주된 목적
  • 몇 개 웹 페이지에서 시작해 그 링크를 따라 나가며 새 콘텐츠를 수집
용도설명
검색 엔진 인덱싱가장 보편적인 용례. 웹 페이지를 모아 검색 인덱스를 만든다
웹 아카이빙나중에 쓰려고 정보를 모아 보존
웹 마이닝데이터에서 유용한 정보 도출
웹 모니터링저작권, 상표권 침해 사례 모니터링 등
좋은 크롤러의 요건설명
규모 확장성웹은 거대하다. 병렬 처리로 효율적으로
안정성 (robustness)잘못된 HTML, 응답 없는 서버, 장애, 악성 링크 같은 비정상 상황에 대응
예절 (politeness)짧은 시간에 너무 많은 요청을 보내지 않는다 (무례하다)
확장성 (extensibility)새로운 형태의 콘텐츠(이미지 등)를 지원하기 쉽게

2. 개략적 설계안

컴포넌트하는 일
시작 URL 집합크롤링 출발점. 주제(쇼핑, 스포츠)나 지역별로 나눠 고르면 좋다
미수집 URL 저장소
(URL Frontier)		아직 다운로드하지 않은 URL 을 저장하는 FIFO 큐
HTML 다운로더URL 로 웹 페이지를 내려받는다
도메인 이름 변환기URL → IP 주소 (DNS)
콘텐츠 파서다운로드한 페이지를 파싱하고 검증 (이상한 페이지는 저장 공간만 낭비)
중복 콘텐츠 거르기이미 저장한 콘텐츠인지 확인. 문서를 해시값으로 비교 (문자열 비교는 느림). 책에 따르면 웹 페이지의 약 29% 가 중복
콘텐츠 저장소HTML 저장. 대부분 디스크, 인기 있는 콘텐츠는 메모리
URL 추출기HTML 에서 링크를 골라낸다. 상대 경로는 절대 경로로 변환
URL 필터특정 콘텐츠 타입, 접속 오류 URL, 차단 목록의 URL 을 제외
URL 저장소
("이미 방문한 URL?")		방문했거나 미수집인 URL 을 추적해 중복을 막는다. 블룸 필터나 해시 테이블 사용

작업 흐름 보충

  1. 시작 URL 들을 미수집 URL 저장소에 넣는다
  2. HTML 다운로더가 저장소에서 URL 을 가져온다
  3. DNS 변환기로 IP 를 얻어 페이지를 내려받는다
  4. 콘텐츠 파서가 HTML 을 파싱·검증한다
  5. 중복 콘텐츠인지 확인한다 (이미 있으면 버림)
  6. 처음이면 콘텐츠 저장소에 저장하고 URL 추출기에 전달
  7. URL 추출기가 링크를 골라내 URL 필터로 보낸다
  8. 필터링 후 이미 처리한 URL 인지 확인 (있으면 버림)
  9. 처음 보는 URL 이면 URL 저장소와 미수집 URL 저장소에 추가

탐색 방식 : DFS vs BFS 보충

  • 웹은 유향 그래프 (페이지 = 노드, 링크 = 에지)
  • DFS : 깊이가 얼마나 깊어질지 가늠하기 어려워 보통 부적합
  • BFS : FIFO 큐를 써서 널리 쓰인다. 단 문제 두 가지
    • 같은 호스트의 링크가 한꺼번에 몰려 그 서버에 부하 (예의 없음)
    • 우선순위를 고려하지 않는다

3. 상세 설계 : 미수집 URL 저장소 (Frontier)

예절, 우선순위, 신선도를 이 저장소가 담당한다.

예절 (politeness)

  • 같은 사이트에 요청을 너무 많이 보내면 서비스 장애(DoS) 처럼 보일 수 있다
  • 원칙 : 같은 사이트의 페이지는 한 번에 한 페이지씩, 요청 사이에 지연을 둔다
  • 구현 : 같은 호스트에 속한 URL 은 언제나 같은 큐(b1, b2 ... bn)로 가도록 보장
  • 호스트 → 큐 매핑 테이블을 두고, 큐 선택기(라우터)가 호스트에 맞는 큐로 보낸다
  • 큐마다 작업 스레드를 하나씩 두어, 스레드는 자기 큐의 URL 만 순서대로 내려받는다

우선순위 (priority)

  • 같은 웹 페이지라도 중요도가 다르다. 페이지랭크, 트래픽 양, 갱신 빈도 등 다양한 척도로 먼저 볼 URL을 정한다
  • 순위결정장치가 URL 의 우선순위를 계산
  • 우선순위별로 큐를 할당 (f1 ... fn). 우선순위가 높으면 더 선택될 확률을 높인다

신선도 (freshness)

  • 웹 페이지는 계속 추가·삭제·변경된다
  • 이미 다운로드한 페이지라도 주기적으로 재수집해 최신 상태를 유지
  • 보충 방법 : 웹 페이지의 변경 이력을 활용 / 우선순위가 높은 페이지는 더 자주 재수집

저장 방식 보충

  • URL 이 수억 개 : 전부 메모리는 공간 부족, 전부 디스크는 느려서 병목
  • → 대부분은 디스크, IO 비용을 줄이려고 메모리 버퍼 큐를 두고 주기적으로 디스크에 기록 (혼합 방식)

4. 상세 설계 : HTML 다운로더 보충

Robots.txt (Robots Exclusion Protocol)

  • 웹 사이트가 크롤러에게 수집해도 되는 페이지를 알리는 표준 파일
  • 크롤링 전에 robots.txt 를 먼저 확인하고 규칙을 따른다. 반복 다운로드를 피하려고 캐싱
성능 최적화설명
분산 크롤링여러 서버에 작업을 나눠 병렬로 (서버마다 여러 스레드)
도메인 이름 변환 결과 캐시DNS 요청이 동기적이라 병목 → 결과를 캐시하고 주기적으로 갱신
지역성 (locality)크롤링 서버를 지역별로 분산 배치해 응답 속도 개선
짧은 타임아웃응답이 느리거나 없는 서버는 일정 시간 뒤 포기 (maxWait)
안정성 / 확장성설명
안정 해시 (5장)다운로더 서버 부하 분산, 서버 추가/삭제 쉬움
크롤 상태 저장장애 시 복구해 이어서 크롤링
예외 처리 / 데이터 검증오류가 나도 전체가 멈추지 않게, 시스템 오류 방지
확장성새 모듈만 끼워 넣기. 예) PNG 다운로더(이미지), 웹 모니터(저작권 침해 감시)

문제 있는 콘텐츠 감지와 회피

문제설명 / 해결
중복 콘텐츠해시/체크섬으로 탐지
거미 덫
(spider trap)		무한히 깊은 링크로 크롤러를 가두는 페이지. 예) .../foo/bar/foo/bar/... → URL 최대 길이를 제한, 사람이 덫을 찾아 필터에 추가
데이터 노이즈광고, 스크립트 코드, 스팸 URL 등 가치 없는 콘텐츠는 제외

5. 추가로 논의할 것 보충

  • 서버 측 렌더링 : JS 로 동적 생성되는 링크는 렌더링한 뒤 파싱
  • 원치 않는 페이지 필터링 (스팸 방지)
  • DB 다중화·샤딩, 서버를 무상태로 해서 수평 확장
  • 가용성, 일관성, 안정성, 데이터 분석

복습 퀴즈 (눌러서 답 확인)

1. 웹 크롤러의 용도 4가지는?

검색 엔진 인덱싱, 웹 아카이빙, 웹 마이닝, 웹 모니터링.

2. 좋은 크롤러의 요건 4가지는?

규모 확장성, 안정성(robustness), 예절(politeness), 확장성(extensibility).

3. 개략적 설계의 흐름을 말해 보자

시작 URL → 미수집 URL 저장소 → HTML 다운로더(+DNS) → 콘텐츠 파서 → 중복 콘텐츠 확인 → 콘텐츠 저장소. 파서에서 URL 추출기 → URL 필터 → 이미 방문한 URL 확인 → 다시 미수집 URL 저장소.

4. BFS 가 흔히 쓰이는 이유와 문제점은?

FIFO 큐로 구현하기 쉽고 깊이가 무한히 들어가지 않는다. 문제는 같은 호스트 링크가 몰려 부하를 주고(예절), 우선순위를 고려하지 못한다는 점.

5. 예절을 지키려면 큐를 어떻게 구성하나?

같은 호스트의 URL 은 항상 같은 큐로 보내고(호스트→큐 매핑), 큐마다 작업 스레드를 하나씩 두어 요청 사이에 지연을 둔다.

6. 우선순위와 신선도는 각각 어떻게 해결하나?

우선순위 : 페이지랭크, 트래픽 양 등으로 순위를 매겨 우선순위별 큐를 두고 높은 큐를 더 자주 선택. 신선도 : 이미 받은 페이지도 주기적으로 재수집하고, 변경 이력과 중요도에 따라 자주 한다.

7. 거미 덫이란? 어떻게 피하나?

크롤러가 끝없이 깊은 링크에 갇히게 만드는 페이지. URL 최대 길이를 제한하고 수동으로 찾아 필터에 추가한다.

8. robots.txt 는?

사이트가 크롤러에게 수집 가능한 페이지를 알려 주는 표준 파일. 크롤링 전에 먼저 확인하고 캐시한다.

더 공부할 거리 보충

  • 페이지랭크 알고리즘
  • 블룸 필터 (URL 중복 확인)
  • 검색 엔진 인덱싱 (역색인), 분산 큐 (Kafka)
