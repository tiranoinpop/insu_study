11장. 뉴스 피드 시스템 설계

홈 화면에 계속 갱신되는 친구들의 소식. 핵심은 팬아웃(fanout).
보충 표시는 공부 노트에 없던 내용을 보강한 부분이다.

1. 뉴스 피드란

  • 홈 페이지 중앙에 지속적으로 갱신되는 스토리 (상태 업데이트, 사진, 비디오, 링크, 친구·페이지·그룹의 소식)
  • 보충 책의 요구사항 : 모바일 앱·웹 / 포스팅을 올리고 친구 피드를 봄 / 시간 역순 정렬(단순화) / 친구 최대 5,000명 / DAU 1천만 / 이미지·비디오 포함

2. 뉴스 피드 API

클라이언트가 서버와 통신하기 위한 수단. HTTP 프로토콜 기반.

API설명
피드 발행 APIPOST /v1/me/feed : 본문(content)과 인증 토큰(auth_token)으로 새 포스팅을 올린다
피드 읽기 APIGET /v1/me/feed : 인증 토큰으로 뉴스 피드를 가져온다

3. 개략적 설계

컴포넌트하는 일
사용자모바일 앱 / 브라우저. 포스팅을 올리는 주체
로드 밸런서트래픽을 웹 서버들로 분산
웹 서버HTTP 요청을 내부 서비스로 중계
포스팅 서비스새 포스팅을 DB 와 캐시에 저장
포스팅 전송 서비스
(팬아웃 서비스)		새 포스팅을 친구의 뉴스 피드에 푸시한다 (뉴스 피드 캐시에 기록)
알림 서비스친구들에게 알리거나 푸시 알림을 보낸다 (10장)

4. 상세 설계

웹 서버

  • 클라이언트와 통신하고 인증(올바른 auth_token 인지), 처리율 제한(4장 : 도배·스팸 방지) 등을 수행

포스팅 전송 서비스 : 팬아웃(fanout)

팬아웃 : 한 사용자의 포스팅을 그 친구 모두에게 전달하는 과정. 두 가지 모델이 있다.

쓰기 시점 팬아웃 (push)읽기 시점 팬아웃 (pull)
시점포스팅을 쓰는 순간 친구들의 피드를 미리 계산해 캐시에 넣음피드를 읽는 순간 친구들의 포스팅을 모아 생성
👍 장점피드가 실시간으로 생성되고, 읽을 때 캐시만 읽으면 되어 빠름비활성 사용자의 피드까지 만드는 낭비가 없다. 핫키 문제 없음
👎 단점친구가 많으면 갱신이 오래 걸림(핫키 문제). 접속 안 하는 사용자의 피드까지 계산해 낭비피드를 읽을 때 만들어서 느리다
혼합 방식 : 대부분의 사용자는 쓰기 시점(push), 친구·팔로어가 아주 많은 유명인은 읽기 시점(pull) 으로 핫키 문제를 피한다. 보충 안정 해시(5장)로 요청과 데이터를 고르게 분산해 핫키를 완화한다.

팬아웃 서비스의 동작

  1. 그래프 DB 에서 친구 ID 목록을 가져온다 (친구 관계 저장에 적합)
  2. 사용자 정보 캐시/DB 에서 친구 정보를 가져온다. 설정으로 차단·음소거한 친구는 제외
  3. 친구 목록 + 새 포스팅 ID 를 메시지 큐에 넣는다
  4. 팬아웃 작업 서버가 큐에서 꺼내 뉴스 피드 캐시에 <post_id, user_id> 순서쌍으로 저장
  • 포스팅 전체 객체가 아니라 ID 만 저장 → 메모리 절약
  • 캐시 크기에 제한을 둔다 (사용자는 보통 최근 포스팅에만 관심)
  • 한 사용자는 여러 개의 <post_id, user_id> 를 갖는다 (여러 친구의 포스팅)

피드 읽기 흐름

  1. 사용자가 뉴스 피드를 읽는 요청을 보낸다
  2. 로드 밸런서가 요청을 웹 서버 중 하나로 보낸다
  3. 웹 서버는 뉴스 피드 서비스를 호출한다
  4. 뉴스 피드 서비스는 뉴스 피드 캐시에서 포스팅 ID 목록을 가져온다
  5. 표시할 사용자 이름, 사진, 콘텐츠 등을 사용자 캐시와 DB 에서 가져와 피드를 완성한다
  6. JSON 형태로 클라이언트에 보낸다

캐시 구조 (5개 계층) 보충

계층저장하는 것

콘텐츠포스팅 데이터. 인기 콘텐츠는 따로 핫 캐시

5. 마무리 : 규모 확장 고려 보충

  • DB 규모 확장 : 수직 vs 수평, SQL vs NoSQL, 주-부 다중화, 읽기용 복제본, 일관성 모델, 샤딩
  • 웹 계층을 무상태로 / 가능한 많은 데이터를 캐시 / 여러 데이터 센터 지원
  • 메시지 큐로 컴포넌트 결합 약화 / 핵심 지표 모니터링 (피크 QPS, 피드 새로고침 지연 시간)

복습 퀴즈 (눌러서 답 확인)

1. 피드 발행 API 와 피드 읽기 API 는?

발행 : POST /v1/me/feed (content, auth_token). 읽기 : GET /v1/me/feed (auth_token).

2. 포스팅 서비스, 팬아웃 서비스, 알림 서비스의 역할은?

포스팅 서비스 : 포스팅을 DB·캐시에 저장. 팬아웃 서비스 : 새 포스팅을 친구들의 뉴스 피드에 전달. 알림 서비스 : 친구들에게 알림·푸시 알림.

3. 쓰기 시점 팬아웃과 읽기 시점 팬아웃의 장단점은?

쓰기 시점 : 읽기가 빠르고 실시간이지만 친구가 많으면 느리고 비활성 사용자 계산이 낭비. 읽기 시점 : 낭비와 핫키 문제가 없지만 읽을 때 느림.

4. 유명인 문제는 어떻게 푸나?

일반 사용자는 쓰기 시점(push), 친구·팔로어가 아주 많은 유명인은 읽기 시점(pull)으로 처리하는 혼합 방식. 안정 해시로 분산해 핫키도 완화.

5. 뉴스 피드 캐시에 포스팅 전체가 아니라 ID 만 저장하는 이유는?

메모리를 아끼기 위해서. 내용은 읽을 때 콘텐츠 캐시/DB 에서 가져온다.

6. 피드 읽기 흐름 6단계는?

읽기 요청 → 로드 밸런서 → 웹 서버 → 뉴스 피드 서비스 → 피드 캐시에서 포스팅 ID 목록 → 사용자·콘텐츠 정보로 피드 완성 → JSON 응답.
