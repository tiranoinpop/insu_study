11장. 검색어 자동완성 시스템 설계

검색창에 글자를 입력할 때마다 추천 검색어를 보여 주는 기능 (typeahead, autocomplete). 핵심 자료구조는 트라이.
보충 표시는 공부 노트에 없던 내용을 보강한 부분이다.

1. 요구사항

요구사항설명
빠른 응답 속도입력하는 동안 바로바로 보여야 한다 보충 (페이스북 사례 : 100ms 이내)
연관성자동완성되는 검색어는 입력한 단어와 관련이 있어야 한다
정렬결과는 인기도 같은 순위 모델에 따라 정렬
규모 확장성많은 트래픽(초당 질의)을 감당
고가용성일부 장애가 나도 시스템은 계속 동작
  • 검색창에 글자를 입력할 때마다 검색어 자동완성 백엔드에 요청을 보낸다
  • 보충 책의 가정 : 접두어 일치 / 추천 5개 / DAU 1천만 / 하루 평균 10건 검색 × 건당 20바이트 → 약 24,000 QPS (최대 48,000) / 질의의 20% 가 신규 → 하루 0.4GB 증가

2. 개략적 설계안

서비스하는 일
데이터 수집 서비스사용자가 입력한 검색어와 빈도를 실시간으로 모아 집계
질의 서비스주어진 접두어로 시작하는 검색어 중 인기 상위 k 개를 돌려줌
  • 데이터 수집 서비스는 검색어 - 빈도 테이블에 쌓는다 (같은 검색어가 들어오면 빈도 +1)
  • 보충 이 테이블에 WHERE query LIKE 'be%' ORDER BY frequency DESC LIMIT 5 같은 SQL 을 쓰면 데이터가 많을 때 DB 가 병목이 된다 → 트라이를 쓴다

3. 트라이 (trie) 자료구조

  • 문자열들을 간략하게 저장할 수 있는 자료구조. 문자열을 꺼내는 연산에 초점을 맞춰 설계됨 (retrieval 에서 이름이 유래 보충)
  • 트리 형태. 루트 노드는 빈 문자열
  • 각 노드는 글자 하나를 저장하고, 영문이라면 26개(a~z) 의 자식 노드를 가질 수 있다
  • 어떤 노드에서 끝나는 단어는 유효 노드로 표시하고, 빈도 정보도 저장한다 (이용 빈도에 따라 정렬된 결과를 주기 위해)

검색어 찾는 법 : 예) 사용자가 "be" 를 입력

  1. 접두어 노드 "be" 를 찾는다
  2. 그 노드에서 시작하는 하위 트리를 탐색해 모든 유효 노드를 찾는다
  3. 유효 노드를 빈도로 정렬해 상위 2개(k개)만 고른다 → 인기 검색어
단계시간 복잡도
접두어 노드 찾기O(p)  (p = 접두어 길이)
하위 트리 전체 순회O(c)  (c = 해당 노드 아래 자식 노드 수)
정렬해서 k 개 고르기O(c log c)
합계O(p) + O(c) + O(c log c)

접두어가 짧고 하위 트리가 크면 매번 전체를 훑고 정렬해야 해서 느리다. 그래서 아래 두 가지로 최적화한다.

최적화 1 : 접두어 최대 길이를 제한

  • 사용자는 아주 긴 검색어를 입력하지 않는다 (보충 예 : 최대 50자)
  • 그러면 접두어 노드 찾기가 O(p) → O(1) (상수 시간)

최적화 2 : 각 노드에 인기 검색어를 캐시

  • 각 노드에 그 아래 상위 k 개 검색어를 미리 저장해 둔다
  • 접두어 노드를 찾으면 바로 답이 있으므로 O(1)
  • 트레이드오프 : 저장 공간을 더 쓰는 대신 응답 속도를 얻는다
방식접두어 노드 찾기상위 k 개 구하기합계
기본O(p)O(c) + O(c log c)느림
길이 제한 + 노드 캐시O(1)O(1)O(1)

4. 상세 설계

데이터 수집 서비스

  • 실시간으로 트라이를 갱신하면 질의 서비스가 느려진다 (매일 수억 건 질의). 게다가 자주 갱신할 필요가 없다 (상위 추천어는 쉽게 바뀌지 않음)
  • 그래서 일정 주기(예 : 주 1회) 로 모아서 트라이를 새로 만든다
컴포넌트하는 일
데이터 분석 서비스 로그검색창에 입력된 원본 질의를 로그로 저장 (append only, 색인 안 함)
로그 취합 서버로그를 집계해 쓸 수 있게 가공. 주 단위가 일반적. 실시간성이 중요한 서비스(예: 트위터)는 더 짧은 주기
작업 서버주기적으로 트라이를 만드는 서버 집합
트라이 캐시분산 캐시. 트라이를 메모리에 두어 읽기 성능을 높임. 주 단위로 DB 스냅샷을 받아 갱신
트라이 DB지속성 저장소. 보충 문서 저장소(트라이 전체를 직렬화해 보관) 또는 키-값 저장소(접두어 → 노드 데이터, 4장)

질의 서비스

  • 검색어를 API 서버에 보내면 트라이 캐시에서 자동완성 결과를 받아 돌려준다 (캐시에 없으면 트라이 DB 에서 읽어 채움) 보충
  • 최적화 방안
    • AJAX 요청 : 페이지 새로고침 없이 요청/응답
    • 브라우저 캐싱 : 자동완성 제안은 짧은 시간엔 잘 안 바뀌므로 결과를 브라우저가 저장 (Cache-Control: private, max-age=3600 등) 보충
    • 보충 데이터 샘플링 : 모든 요청을 로그로 남기지 않고 N 건 중 1건만 기록해 처리량을 줄임

트라이 연산

연산설명
트라이 생성작업 서버가 데이터 분석 서비스의 집계 데이터로 만든다
트라이 갱신① 매주 새 트라이를 만들어 교체 ② 개별 노드를 갱신 (느리다. 노드를 바꾸면 조상 노드의 캐시된 인기 검색어까지 모두 고쳐야 함)
검색어 삭제혐오·폭력·위험한 검색어를 막아야 함. 트라이 캐시 앞에 필터 계층을 두고 부적절한 질의어가 반환되지 않도록 한다. 필터 규칙에 따라 DB 에서는 비동기로 지운다

저장소 규모 확장 : 샤딩

  • 영문 검색어를 첫 글자 기준으로 나눠 서버를 분산 (예 : a~m 은 서버 1, n~z 는 서버 2). 더 늘리면 첫 두 글자 기준
  • 글자마다 시작하는 단어 수가 달라(s 로 시작하는 단어가 x 보다 훨씬 많음) 균등하지 않다
  • 보충 → 샤드 맵 관리자를 두고 검색어 빈도를 분석해 균형 있게 나눈다 (예 : s 하나, u~z 하나)
  • 샤딩은 작업 대상 데이터 양을 줄여 준다 (1장 샤딩)

5. 확장 논의 보충

주제방법
다국어 지원트라이에 유니코드 데이터를 저장
국가별로 인기 검색어가 다름국가별로 다른 트라이를 사용하고, 응답 속도를 위해 CDN 에 저장 (1장 CDN)
실시간 검색어 추이 반영① 샤딩으로 작업 대상 데이터 양을 줄인다 ② 순위 모델을 바꿔 최근 검색어에 더 높은 가중치를 준다 ③ 데이터를 스트림으로 처리 (Spark Streaming 등)

복습 퀴즈 (눌러서 답 확인)

1. 자동완성의 두 서비스는?

데이터 수집 서비스(검색어·빈도 집계)와 질의 서비스(접두어에 맞는 상위 k 개 반환).

2. 트라이란? 각 노드가 저장하는 것은?

문자열을 글자 단위 트리로 저장하는 자료구조. 루트는 빈 문자열이고 각 노드는 글자 하나. 단어가 끝나는 유효 노드와 빈도 정보를 저장한다.

3. "be" 를 입력했을 때 추천어를 구하는 3단계와 시간 복잡도는?

접두어 노드 찾기 O(p) → 하위 트리의 유효 노드 순회 O(c) → 정렬해서 상위 k 개 O(c log c).

4. 두 가지 최적화는?

접두어 최대 길이 제한(O(p) → O(1)), 각 노드에 상위 인기 검색어 캐시(상위 k 개를 O(1) 에). 공간을 더 쓰고 속도를 얻는다.

5. 트라이를 왜 실시간으로 갱신하지 않나?

매일 수억 건 질의를 실시간으로 반영하면 질의 서비스가 느려지고, 상위 추천어는 자주 바뀌지 않아서 주기적으로(예 : 주 1회) 새로 만들면 충분하다.

6. 부적절한 검색어는 어떻게 막나?

트라이 캐시 앞에 필터 계층을 두어 반환되지 않게 하고, DB 에서는 규칙에 따라 비동기로 삭제한다.

7. 첫 글자 기준 샤딩의 문제와 해결은?

글자마다 단어 수가 달라 불균등하다. 샤드 맵 관리자가 검색어 빈도를 분석해 균형 있게 나눈다.

더 공부할 거리 보충

  • 트라이 구현 (자바스크립트로 직접 만들어 보기), 압축 트라이(radix tree)
  • 디바운싱(debounce) : 입력이 멈춘 뒤에 요청 보내기 (프론트엔드 최적화)
  • Elasticsearch 의 completion suggester
