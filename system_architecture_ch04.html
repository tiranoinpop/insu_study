4장. 처리율 제한 장치의 설계

Rate Limiter. 2장(개략적 규모 추정), 3장(면접 공략법)은 정리를 생략했다.
보충 표시는 공부 노트에 없던 내용을 보강한 부분이다.

1. 처리율 제한 장치란

  • 클라이언트 또는 서비스가 보내는 트래픽의 처리율을 제어하는 장치
  • 임계치를 넘는 요청은 차단
  • 보충 예) 하루 글 작성 횟수 제한, 같은 IP 로 계정 생성 횟수 제한, 같은 기기로 주당 리워드 횟수 제한
왜 쓰나설명
DoS 방지Denial of Service 공격에 의한 자원 고갈 방지
비용 절감서버를 적게 둘 수 있고, 유료 외부 API 호출 횟수를 줄인다
서버 과부하 방지봇이나 잘못된 이용 패턴의 트래픽을 걸러낸다

2. 어디에 둘 것인가

위치평가
클라이언트요청을 쉽게 위변조할 수 있다 → 부적합
서버API 서버 안에 직접 구현
미들웨어 (게이트웨이)서버 앞에서 걸러낸다. 초과 시 HTTP 429 (Too Many Requests)

API 게이트웨이 : 처리율 제한, SSL 종단, 인증, IP 허용 목록 등을 지원하는 완전 관리형 서비스.

보충 판단 기준 : ① 현재 기술 스택이 서버 측 구현을 잘 지원하나 ② 비즈니스에 맞는 알고리즘을 고를 수 있나 (제3자 게이트웨이는 제한적일 수 있음) ③ 이미 마이크로서비스 + API 게이트웨이를 쓰면 거기에 넣는 게 낫다 ④ 직접 만들 개발 인력이 충분한가

3. 처리율 제한 알고리즘 5가지

3-1. 토큰 버킷 (token bucket)

  • 정해진 용량의 버킷에 토큰이 주기적으로 채워진다 (가득 차면 넘치는 건 버림)
  • 요청 1개 = 토큰 1개 소비. 토큰이 있으면 처리, 없으면 버린다
  • 파라미터 : 버킷 크기, 토큰 공급률
  • 버킷은 보통 API 엔드포인트별(또는 사용자·IP별)로 둔다
  • 👍 구현 쉬움, 메모리 효율적, 짧은 시간의 burst 트래픽도 처리 (토큰이 남아 있는 한)
  • 👎 두 파라미터를 적절히 튜닝하기 어렵다
  • 사용처 : Amazon, Stripe

3-2. 누출 버킷 (leaky bucket)

  • 토큰 버킷과 비슷하지만 처리율이 고정. 보통 FIFO 큐로 구현
  • 요청이 오면 큐에 자리가 있으면 추가, 가득 찼으면 버린다. 정해진 시간마다 큐에서 꺼내 처리
  • 파라미터 : 큐 크기, 처리율(초당 몇 개 처리)
  • 👍 메모리 효율적, 안정적인 출력이 필요할 때 적합
  • 👎 단시간에 몰리면 큐에 오래된 요청이 쌓여 최신 요청이 버려질 수 있다, 튜닝이 어렵다
  • 사용처 : Shopify

3-3. 고정 윈도 카운터 (fixed window counter)

  • 타임라인을 고정 간격의 윈도로 나누고 윈도마다 카운터를 둔다. 요청이 오면 +1, 임계치에 도달하면 그 윈도가 끝날 때까지 버린다
  • 👍 메모리 효율적, 이해하기 쉬움
  • 👎 윈도 경계 부근에 트래픽이 몰리면 허용량보다 많이 통과한다
  • 보충 예) 분당 5개 제한 : 2:00:30~2:01:00 에 5개 + 2:01:00~2:01:30 에 5개 → 1분 사이에 10개 통과 (최대 2배)

3-4. 이동 윈도 로깅 (sliding window log)

  • 고정 윈도의 경계 문제를 해결. 요청의 타임스탬프를 로그로 저장 (Redis sorted set 등)
  • 새 요청이 오면 윈도를 벗어난 오래된 타임스탬프를 지우고, 새 것을 추가한 뒤 로그 크기가 허용치 이하면 처리, 아니면 거부
  • 👍 어떤 순간의 윈도를 봐도 허용량을 정확히 지킨다
  • 👎 메모리를 많이 쓴다 (거부된 요청의 타임스탬프도 저장)

3-5. 이동 윈도 카운터 (sliding window counter)

  • 고정 윈도 카운터 + 이동 윈도 로깅의 결합
  • 현재 윈도 요청 수 + 직전 윈도 요청 수 × 겹치는 비율
  • 보충 예) 분당 7개 제한, 직전 1분에 5개, 현재 1분의 30% 시점에 3개 → 3 + 5 × 0.7 = 6.5 → 7 미만이므로 허용
  • 👍 순간 폭증에 강하고 메모리 효율적
  • 👎 직전 윈도 요청이 균등하다고 가정한 추정치 (Cloudflare 실험 오차율 0.003%)

4. 개략적 아키텍처

  • 핵심 : 요청 수를 추적할 카운터를 어디에 저장할까?
  • DB 는 디스크 접근이라 느리다 → 메모리 캐시(Redis) 사용. 시간 기반 만료 지원
  • 보충 Redis 명령 : INCR (카운터 +1), EXPIRE (시간이 지나면 카운터 자동 삭제)
클라이언트
→ 처리율 제한 미들웨어
   (Redis 에서 카운터 조회/증가)
→ 한도 미만 : API 서버로 전달
→ 한도 초과 : 429 반환

5. 상세 설계 보충

  • 규칙 : 설정 파일(YAML 등)로 디스크에 저장, 작업 프로세스가 주기적으로 읽어 캐시에 올린다
  • 한도 초과 시 : HTTP 429 반환. 경우에 따라 요청을 큐에 보관해 나중에 처리
응답 헤더의미
X-Ratelimit-Remaining윈도 내 남은 처리 가능 요청 수
X-Ratelimit-Limit윈도마다 보낼 수 있는 요청 수
X-Ratelimit-Retry-After몇 초 뒤에 다시 보내야 하는지

6. 분산 환경에서의 구현

두 가지 어려운 문제가 있다 : 경쟁 조건, 동기화.

문제설명해결
경쟁 조건
(race condition)		 두 요청이 동시에 카운터를 읽고(예: 3) 각각 +1 해서 쓰면 5 가 되어야 할 값이 4 가 된다 (읽기-수정-쓰기 사이에 끼어듦) Lua 스크립트, Redis sorted set (락은 시스템을 느리게 함)
동기화
(synchronization)		 웹 계층은 무상태라 같은 클라이언트 요청이 다른 제한 장치로 갈 수 있다. 서로 정보를 모르면 제대로 제한 못 함 고정 세션은 확장성이 떨어져 비추천 → Redis 같은 중앙 집중형 저장소

성능 최적화

  • 여러 데이터 센터 + 사용자와 가까운 에지 서버로 지연 시간 감소
  • 제한 장치 간 데이터 동기화는 최종 일관성(eventual consistency) 모델 사용

모니터링

  • 목적 : 채택한 알고리즘과 규칙이 효과적인지 확인
  • 규칙이 너무 빡빡해 정상 요청이 많이 버려지면 → 규칙 완화
  • flash sale 같은 급증 트래픽에서 비효율적이면 → 알고리즘 교체 (예: 토큰 버킷으로 burst 허용)

7. 그 밖에 생각해볼 것 보충

  • 경성(hard) vs 연성(soft) 제한 : 임계치를 절대 못 넘나, 잠시 넘을 수 있나
  • 계층 : 지금까지는 애플리케이션 계층(7계층). Iptables 로 IP 계층(3계층)에서도 가능
  • 클라이언트 모범 사례 : 캐시로 API 호출 줄이기 / 한도 이해 / 예외 처리 / 재시도는 충분한 백오프(back-off)

복습 퀴즈 (눌러서 답 확인)

1. 처리율 제한을 클라이언트에 두면 안 되는 이유는?

요청을 쉽게 위변조할 수 있어서 안정적으로 강제할 수 없다.

2. 토큰 버킷의 두 파라미터는? burst 를 처리할 수 있는 이유는?

버킷 크기, 토큰 공급률. 토큰이 버킷에 쌓여 있는 만큼은 한꺼번에 소비할 수 있어서.

3. 누출 버킷과 토큰 버킷의 가장 큰 차이는?

누출 버킷은 큐를 통해 처리율이 고정이라 안정적이지만 burst 에 약하고, 토큰 버킷은 burst 를 허용한다.

4. 고정 윈도 카운터의 문제와 해결 방법은?

윈도 경계에 몰린 요청이 최대 2배 통과한다. 이동 윈도 로깅(정확, 메모리 많음) 또는 이동 윈도 카운터(추정, 메모리 적음)로 해결.

5. 한도 초과 시 반환하는 HTTP 상태 코드는?

429 Too Many Requests

6. 분산 환경의 두 가지 문제와 해결책은?

경쟁 조건 → Lua 스크립트 / sorted set. 동기화 → Redis 같은 중앙 집중형 저장소.

더 공부할 거리 보충

  • Redis 의 INCR / EXPIRE, Lua 스크립팅, sorted set
  • 서킷 브레이커, 백오프 + 지터(jitter)
  • API 게이트웨이 (AWS API Gateway, Kong, Nginx rate limit)
