10장. 알림 시스템 설계

Notification System. 1장의 메시지 큐, 4장의 처리율 제한이 쓰인다.
보충 표시는 공부 노트에 없던 내용을 보강한 부분이다.

1. 알림의 종류

  • 인기 있는 기능 : 모바일 푸시 알림, SMS 메시지, 이메일
  • 보충 책의 요구사항 : soft real-time(약간 지연 OK) / iOS·Android·PC 지원 / 사용자가 알림을 끌 수 있음(opt-out) / 하루 푸시 1천만, SMS 100만, 이메일 500만 건

2. 알림 유형별 전달 구조

유형구성 요소
iOS 푸시알림 제공자 → APNS (Apple Push Notification Service) → 단말
Android 푸시알림 제공자 → FCM (Firebase Cloud Messaging) → 단말
SMS알림 제공자 → SMS 서비스 (Twilio, Nexmo 등) → 단말
이메일알림 제공자 → 이메일 서비스 (SendGrid, Mailchimp 등) → 단말
  • 알림 제공자(provider) : 알림 요청을 만들어 제3자 서비스로 보내는 주체. 필요한 것
    • 단말 토큰 (device token) : 알림 요청을 보내는 데 쓰는 고유 식별자
    • 페이로드 (payload) : 알림 내용을 담은 JSON
  • 보충 앱 설치·가입 때 단말 토큰, 전화번호, 이메일을 받아 DB 에 저장. 한 사용자가 여러 단말을 가질 수 있다
{
  "aps": {
    "alert": { "title": "새 메시지", "body": "인수님이 댓글을 달았어요" },
    "badge": 5
  }
}

3. 개략적 설계안

  1. 1 ~ N 개 서비스가 알림 시스템에 알림 전송을 요청(API)
  2. 알림 시스템이 제3자 서비스에 전달할 알림 페이로드를 만든다
  3. 제3자 서비스(APNS, FCM, SMS 서비스, 이메일 서비스)가 실제로 사용자에게 전달
문제점설명
SPOF알림 서버가 하나뿐이면 장애 시 전체가 멈춘다
확장 어려움DB, 캐시, 처리 로직을 한 서버가 다 맡음 보충
성능 병목알림 생성과 제3자 응답 대기 같은 자원 집약적 작업을 한곳에서 처리 보충

개선안

  • 데이터베이스와 캐시를 알림 시스템의 주 서버에서 분리
  • 알림 서버를 무상태(stateless) 로 만든다
  • 알림 서버를 증설하고 자동으로 수평 확장이 이루어지게 한다
  • 메시지 큐로 시스템 컴포넌트 사이의 강한 결합을 끊는다 (유형별로 큐를 분리)

개선된 흐름

  1. 서비스가 API 를 호출해 알림 서버로 알림을 보낸다
  2. 알림 서버가 사용자 정보, 단말 토큰, 알림 설정 같은 메타데이터를 캐시나 DB 에서 가져온다
  3. 알림 서버가 전송할 알림에 맞는 이벤트를 만들어 해당 큐에 넣는다
  4. 작업 서버가 메시지 큐에서 알림 이벤트를 꺼낸다
  5. 작업 서버가 알림을 제3자 서비스로 보낸다
  6. 제3자 서비스가 사용자 단말로 알림을 전송한다

보충 알림 서버의 기능 : 알림 전송 API 제공(스팸 방지를 위해 인증된 클라이언트만) / 이메일 주소·전화번호 기본 검증 / 캐시·DB 조회 / 알림 데이터를 큐에 넣기

4. 고려할 사항들

안정성

항목설명
데이터 손실 방지알림이 소실되면 안 된다 → 알림 로그를 DB 에 유지하고 재시도
알림 중복 전송 방지분산 시스템 특성상 완전히 막기는 어렵다. 보충 이벤트 ID 로 이미 보낸 알림인지 확인하는 중복 탐지로 줄인다

그 밖에

항목설명
알림 템플릿형식을 미리 만들어 두고 매개변수만 채움 → 일관성, 작업 시간 단축
알림 설정사용자별·채널별 수신 여부를 알림 설정 테이블에 보관
전송률 제한사용자에게 보내는 알림 수 제한 (너무 많으면 꺼 버림) → 4장
재시도 방법제3자 전송 실패 시 다시 큐에 넣어 재시도
푸시 알림 보안 보충인증된 클라이언트만 보낼 수 있게 appKey, appSecret 사용
큐 모니터링큐에 쌓인 알림 수가 많으면 작업 서버가 부족 → 증설
이벤트 추적알림 열람률, 클릭률, 앱 사용(engagement) 을 추적 (분석 서비스 연동)

복습 퀴즈 (눌러서 답 확인)

1. iOS 푸시를 보내기 위한 세 가지 컴포넌트는? Android 는?

iOS : 알림 제공자, APNS, 단말. Android : 알림 제공자, FCM, 단말.

2. 단말 토큰과 페이로드는?

단말 토큰 : 알림을 보낼 단말을 가리키는 고유 식별자. 페이로드 : 알림 내용을 담은 JSON.

3. 첫 설계의 문제점과 개선안은?

알림 서버가 하나라 SPOF 이고 확장이 어렵다. 개선 : DB·캐시 분리, 알림 서버 무상태화와 증설(자동 확장), 메시지 큐로 결합 약화.

4. 메시지 큐를 쓰면 좋은 점은?

알림 서버와 작업 서버가 느슨하게 결합되어 각각 독립적으로 확장·장애 대응이 가능하고, 제3자 응답이 느려도 알림 서버가 막히지 않는다.

5. 알림 중복 전송을 완전히 막기 어려운 이유와 줄이는 방법은?

분산 시스템에서는 재시도 등으로 같은 알림이 두 번 갈 수 있다. 이벤트 ID 를 확인해 이미 보낸 알림이면 버리는 방식으로 줄인다.

6. 큐 모니터링으로 무엇을 알 수 있나?

큐에 쌓인 알림이 많으면 작업 서버가 부족하다는 신호이므로 작업 서버를 늘린다.

더 공부할 거리 보충

  • APNS / FCM 동작 방식, 단말 토큰 갱신
  • 큐 기반 재시도와 Dead Letter Queue
  • 알림 분석 (열람률, 전환율)
