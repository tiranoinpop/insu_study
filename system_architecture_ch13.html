13장. 구글 드라이브 설계

파일을 클라우드에 저장하고 여러 단말에서 동기화·공유하는 서비스 (Google Drive, Dropbox). 핵심은 블록 단위 동기화.
보충 표시는 공부 노트에 없던 내용을 보강한 부분이다.

1. 요구사항

요구사항설명
안정성저장소 시스템에서 데이터 손실은 절대 있으면 안 된다
빠른 동기화 속도동기화가 느리면 사용자가 인내심을 잃는다
네트워크 대역폭불필요한 네트워크 사용을 줄여야 한다 (모바일 데이터 요금)
규모 확장성아주 많은 트래픽을 처리
높은 가용성일부 서버가 죽거나 네트워크가 끊겨도 계속 사용
  • 보충 기능 : 파일 추가(드래그 앤 드롭) / 다운로드 / 여러 단말 동기화 / 파일 갱신 이력(revision history) / 파일 공유 / 편집·삭제·공유 시 알림. 구글 문서 같은 공동 편집은 제외
  • 보충 책의 가정 : 가입 5천만, DAU 1천만, 사용자당 10GB 무료 → 총 500PB / 하루 평균 업로드 2건(500KB) / 업로드 QPS 약 240 (최대 480)

2. 간단하게 시작

  • 파일을 올리고 내려받는 웹 서버
  • 사용자 데이터, 로그인 정보, 파일 정보 같은 메타데이터를 보관할 데이터베이스
  • 파일을 저장할 저장소 (처음엔 서버 디스크 → 용량이 모자라면 샤딩 → 결국 S3 같은 클라우드 저장소)

API

API설명
1. 파일 업로드 API보충 단순 업로드(작은 파일), 이어 올리기(resumable) (큰 파일, 네트워크 장애로 끊겨도 이어서) : POST /files/upload?uploadType=resumable
2. 파일 다운로드 API보충 GET /files/download (path 로 파일 지정)
3. 파일 갱신 히스토리 API보충 GET /files/list_revisions (path, limit)

보충 모든 API 는 사용자 인증과 HTTPS(SSL) 가 필요하다.

개선 (한 서버 → 분산)

  • 로드 밸런서로 네트워크 트래픽을 분산, 웹 서버는 로드 밸런서 덕분에 손쉽게 추가할 수 있다
  • 메타데이터 데이터베이스를 분리 (SPOF 방지 → 다중화·샤딩)
  • 파일 저장소 S3 : 가용성·내구성이 높고, 여러 지역에 다중화

보충 동기화 충돌 : 두 사용자가 같은 파일을 동시에 고치면 먼저 처리된 쪽이 이긴다. 나중 쪽은 충돌이 나서, 시스템이 충돌 사본을 만들어 둘 다 보여 주고 사용자가 직접 병합하게 한다.

3. 블록 저장소 서버

큰 파일을 통째로 올리면 조금만 고쳐도 파일 전체를 다시 보내야 해서 대역폭이 낭비된다. 그래서 파일을 블록으로 쪼갠다.

  • 델타 동기화(delta sync) : 파일이 수정되면 수정이 일어난 블록만 동기화
  • 압축 : 블록 단위로 압축해 크기를 줄임 (보충 텍스트는 gzip/bzip2, 이미지·비디오는 다른 알고리즘)
  • 암호화 : 클라우드 저장소로 보내기 전에 블록을 암호화
  • 보충 블록 크기는 최대 4MB (Dropbox)
  1. 주어진 파일을 작은 블록들로 분할
  2. 각 블록을 압축
  3. 클라우드 저장소로 보내기 전에 암호화
  4. 클라우드 저장소로 보낸다

4. 업로드 절차

두 개의 요청이 병렬로 일어난다 : 파일 메타데이터 추가(1~4), 파일 업로드(5~10).

단계하는 일
파일 메타데이터 추가
1클라이언트 1 이 파일 메타데이터 추가 요청 (API 서버)
2새 파일의 메타데이터를 DB 에 저장하고 업로드 상태를 "대기중"으로 변경
3새 파일이 추가되었음을 알림 서비스에 통지
4알림 서비스가 관련된 클라이언트(클라이언트 2)에게 업로드 알림
파일 업로드
5클라이언트 1 이 파일을 블록 저장소 서버에 업로드
6블록 저장소 서버가 블록 단위로 압축하고 암호화한 다음 클라우드 저장소에 전송
7업로드가 끝나면 클라우드 저장소가 완료 콜백을 호출 (API 서버로)
8메타데이터 DB 에서 파일의 상태를 "완료" 로 변경
9알림 서비스에 업로드가 끝났음을 통지
10알림 서비스가 다른 클라이언트에게 파일 업로드가 끝났음을 알림

다운로드 절차

  • 다른 클라이언트가 알림 서비스를 통해 파일이 추가·편집된 사실을 알게 된다
  • 클라이언트가 오프라인이면 변경 사실을 저장해 두었다가, 네트워크 상태가 접속 중으로 바뀌면 그때 새 버전을 가져가도록 한다
  • 보충 흐름 : 알림 → 클라이언트 2 가 API 서버에 메타데이터 요청 → 메타데이터 DB 에서 변경 사항 조회 → 클라이언트가 블록 저장소 서버에서 필요한 블록만 내려받아 파일을 재구성

알림 서비스

  • 파일의 일관성을 유지하려고, 클라이언트는 로컬에서 파일 수정이 감지되면 그 사실을 알려 충돌 가능성을 줄여야 한다. 그 목적으로 알림 서비스를 이용한다
  • 이벤트 데이터를 클라이언트에게 전달하는 서비스
  • 보충 롱 폴링(Dropbox) vs 웹소켓 : 여기서는 서버 → 클라이언트 단방향 알림이면 충분하고, 알림 빈도가 낮고 한 번에 많은 데이터를 보내지 않아서 롱 폴링을 쓴다. 채팅(10장)은 양방향이라 웹소켓
메타데이터 DB 테이블 보충설명
user사용자 기본 정보 (이름, 이메일, 프로필 사진)
device단말 정보 (푸시 알림용 push_id). 한 사용자가 여러 단말
namespace사용자의 루트 디렉터리
file파일 최신 정보
file_version파일 갱신 이력. 읽기 전용(수정 불가, 무결성 보장)
block파일 블록 정보. 올바른 순서로 합치면 어떤 버전이든 복원 가능

5. 저장소 공간 절약

여러 버전을 보관하니 저장소 용량이 빠르게 늘어난다.

방법설명
중복 제거계정 안에서 해시값이 같은 블록은 하나만 저장
지능적 백업 전략보충 한도 설정 : 보관할 버전 수에 상한을 둔다. 중요한 버전만 보관 (자주 쓰이는 최근 것 위주)
아카이빙 저장소자주 쓰이지 않는 데이터를 아카이빙 저장소로 옮긴다 (예 : S3 Glacier. 훨씬 저렴)

6. 장애 처리

장애대응
로드 밸런서부 로드 밸런서가 이어받아야 한다 (박동 신호로 서로 상태를 모니터링)
블록 저장소 서버다른 서버가 미완료·대기 작업을 이어받는다
클라우드 저장소S3 버킷은 여러 지역에 다중화되므로 한 지역에서 장애가 나면 다른 지역에서 가져온다
API 서버무상태 서버라 로드 밸런서가 장애 서버를 격리하고 다른 서버로 요청을 보낸다
메타데이터 캐시보충 여러 대로 다중화. 한 노드가 죽어도 다른 노드가 서비스, 새 노드로 교체
메타데이터 DB주-부 : 주가 죽으면 부를 주로 승격, 부가 죽으면 다른 부를 사용 (1장)
알림 서비스접속 중인 사용자마다 롱 폴링 연결을 유지하므로, 서버 한 대가 수십만~백만 연결을 관리한다. 장애 나면 모든 연결이 끊기고 재접속이 한꺼번에 몰려 부하가 큰 문제 → 재접속을 천천히 분산 보충
오프라인 사용자 백업 큐 보충접속하지 않은 사용자의 변경을 큐에 보관. 큐를 다중화하고 장애 시 구독자가 새 큐를 다시 구독

복습 퀴즈 (눌러서 답 확인)

1. 파일을 블록으로 나누는 이유는?

조금만 고쳐도 파일 전체를 다시 보내면 대역폭이 낭비되기 때문. 수정된 블록만 동기화(델타 동기화)하고, 블록 단위로 압축·암호화한다.

2. 블록 저장소 서버가 하는 일 3가지는?

파일을 블록으로 분할, 각 블록 압축, 암호화한 뒤 클라우드 저장소에 전송.

3. 업로드 시 병렬로 일어나는 두 요청은?

파일 메타데이터 추가(상태 "대기중", 알림 서비스 통지)와 파일 본체의 업로드(블록 저장소 → 클라우드 저장소 → 완료 콜백 → 상태 "완료").

4. 알림 서비스는 왜 필요하고 어떤 방식을 쓰나?

다른 클라이언트에 변경 사실을 알려 일관성을 유지하고 충돌 가능성을 줄이기 위해서. 서버→클라이언트 단방향이므로 롱 폴링을 쓴다 (웹소켓은 양방향이 필요한 채팅에 적합).

5. 저장소 공간을 절약하는 방법은?

중복 블록 제거, 보관 버전 수 제한 같은 지능적 백업 전략, 자주 쓰지 않는 데이터를 아카이빙 저장소로 이동.

6. 장애별 대응을 하나씩 말해 보자

로드 밸런서 : 부 LB 가 이어받음 / 블록 서버 : 다른 서버가 작업 인계 / 클라우드 저장소 : 다른 지역 사본 / API 서버 : 무상태라 다른 서버 / DB : 주-부 승격 / 알림 서비스 : 재접속 폭주 주의.

더 공부할 거리 보충

  • rsync 알고리즘, 콘텐츠 정의 청킹(content-defined chunking)
  • S3 의 내구성(99.999999999%)과 스토리지 클래스
  • 충돌 해결과 OT / CRDT (실시간 협업 편집)
