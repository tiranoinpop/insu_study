1장. 사용자 수에 따른 규모 확장성

대규모 시스템 설계 기초.
보충 표시는 공부 노트에 없던 내용을 보강한 부분이다.

1. 단일 서버로 시작

  1. 사용자가 도메인(example.com)으로 접속 → DNS에 질의해 IP 주소로 변환
  2. 받은 IP 로 HTTP 요청
  3. 웹 서버가 HTML 또는 JSON 으로 응답
  • DNS 는 제3자가 제공하는 (유료) 서비스. 우리 시스템의 일부가 아니다
  • 보충 모바일 앱은 보통 JSON 으로 응답받는다 (API)

2. 데이터베이스

  • 사용자가 늘면 서버 한 대로는 부족하다
  • 웹/모바일 트래픽 서버와 데이터베이스 서버(데이터 계층)를 분리 → 각각 독립적으로 확장
구분예시특징
보충 관계형 (RDBMS)MySQL, PostgreSQL, Oracle테이블/행/열, 조인(join) 가능. 대부분은 이걸로 충분
보충 비관계형 (NoSQL)Redis, Cassandra, DynamoDB, MongoDB일반적으로 조인 미지원. 아주 낮은 지연시간, 비정형 데이터, 매우 많은 양의 데이터가 필요할 때

3. 수직적 vs 수평적 규모 확장

구분수직적 (scale up)수평적 (scale out)
방법한 서버의 CPU, 메모리 증설서버 대수를 늘림
장점단순하다대규모 확장에 적합
단점한계가 있다, failover·다중화 불가구조가 복잡해진다
핵심 문제SPOF (Single Point Of Failure, 단일 장애점)부하를 어떻게 나눌까 → 로드 밸런서

트래픽이 적을 땐 수직 확장도 좋은 선택(단순함). 하지만 크게 가려면 수평 확장이 필수.

4. 로드 밸런서

  • 여러 웹 서버에 트래픽 부하를 고르게 분산
  • 사용자는 로드 밸런서의 공개 IP 로 접속, 웹 서버들은 사설 IP 사용 (외부에서 직접 접근 불가 → 보안↑)
  • 서버 하나가 다운돼도 다른 서버로 보낸다 → failover, 가용성↑
  • 트래픽이 늘면 서버를 더 추가하면 끝
  • 웹 서버가 stateless 해야 수평 확장이 쉽다 (→ 7번)

5. 데이터베이스 다중화 (replication)

역할하는 일
주 (master)쓰기 (INSERT, UPDATE, DELETE)
부 (slave)주의 사본을 받아 읽기만

대부분의 서비스는 읽기가 쓰기보다 훨씬 많다 → 부 서버가 더 많다.

장애 시나리오

상황대응
부가 한 대뿐인데 다운읽기도 일시적으로 주가 처리, 새 부를 붙임
부가 여러 대, 한 대 다운나머지 부가 읽기 처리
주가 다운부 중 한 대가 새 주로 승격

보충 승격하는 부의 데이터가 최신이 아닐 수 있다 (복제 지연, replication lag). 누락 데이터는 복구 스크립트로 채우거나 다중 마스터 같은 더 복잡한 구성을 쓰기도 한다.

여기까지의 요청 흐름

사용자 → DNS → (IP)
→ 로드 밸런서
→ 웹 서버 여러 대
   - 쓰기 → DB 주
   - 읽기 → DB 부 (여러 대)

6. 응답 시간 개선

캐시 (cache)

  • 비싼 연산 결과 / 자주 쓰는 데이터를 메모리에 잠시 보관 → 이후 요청이 빨라지고 DB 부하↓
  • 웹 서버가 매번 DB 에 묻는 것보다 훨씬 빠르다
  • 동작: 요청 → 캐시에 있나? → 있으면 hit 바로 반환 / 없으면 miss → DB 조회 후 캐시에 저장하고 반환
고려할 점내용
보충 어떤 데이터?읽기는 많고 수정은 드문 데이터
보충 만료 (expiration)너무 짧으면 DB 를 자주 읽고, 너무 길면 원본과 달라진다
보충 일관성 (consistency)DB 와 캐시가 어긋날 수 있다
보충 SPOF캐시 서버가 한 대면 SPOF → 여러 대 + 여유 메모리
보충 제거 (eviction)꽉 차면 뭘 버릴까 → LRU(가장 오래 안 쓴 것), LFU(가장 적게 쓴 것), FIFO

보충 메모리라서 재시작하면 사라진다. 중요한 데이터를 캐시에만 두지 않는다.

CDN (Content Delivery Network)

  • 정적 콘텐츠(이미지, 동영상, CSS, JS)를 전 세계에 분산된 서버에 두고 가까운 곳에서 전달
  • 동작: 사용자가 이미지 URL 요청 → CDN 에 없으면 원본(origin)에서 가져와 저장+반환 → 다음 사용자부터는 CDN 에서 바로 반환
  • 보충 고려할 점 : 비용(전송량 과금) / 적절한 만료 시기(TTL) / CDN 장애 시 원본으로 우회 / 바뀐 파일 무효화(invalidation)

7. 무상태(stateless) 웹 계층

구분상태 유지 (stateful)무상태 (stateless)
상태 정보서버 안에 기억 (세션 등)서버 밖 공유 저장소에 둠 (Redis, NoSQL)
요청 처리같은 사용자는 항상 같은 서버로 가야 함 (클라이언트와 서버가 바인딩)어떤 서버가 받아도 같은 결과
확장어렵다쉽고 단순하고 안정적
  • 고정 세션(sticky session)으로 해결할 수는 있지만 부하 분산이 비효율적이고 서버 추가/제거가 어렵다
  • 보충 무상태가 되면 오토스케일링(트래픽에 따라 서버 자동 증감)이 가능해진다

8. 데이터 센터

  • 장애 없을 때 : 사용자를 가장 가까운 데이터 센터로 안내 = 지리적 라우팅
  • 장애 발생 : 멀더라도 가용한 데이터 센터로 안내
  • 보충 기술적으로 풀어야 할 것 : 트래픽 우회(DNS) / 데이터 동기화(센터마다 DB 가 따로라 여러 센터에 복제) / 어디서든 같은 서비스가 동작하는지 테스트·배포 자동화
핵심 : 시스템을 큰 규모로 확장하려면 컴포넌트를 분리해서 각기 독립적으로 확장될 수 있어야 한다.

9. 메시지 큐

  • 메시지의 무손실을 보장하는 비동기 통신 컴포넌트
  • 생산자(producer) 가 메시지를 큐에 넣고 → 소비자(consumer) 가 꺼내 처리
  • 서비스/서버 간 결합이 느슨해진다 : 소비자가 죽어 있어도 생산자는 발행 가능, 반대도 마찬가지
  • 보충 예) 사진 보정 : 웹 서버가 작업을 큐에 넣고 워커들이 처리. 큐가 길어지면 워커를 늘리고 비면 줄인다 → 독립적 확장
  • 보충 대표 제품 : RabbitMQ, Kafka, SQS

10. 로그, 메트릭, 자동화 보충

  • 로그 : 에러 로그를 서버별로 보지 않고 한곳에 모아 본다
  • 메트릭 : 호스트(CPU, 메모리, 디스크) / 서비스 전체 성능(DAU, 수익, 쿼리 성능) / 비즈니스 지표
  • 자동화 : 지속적 통합(CI), 빌드·테스트·배포 자동화 → 생산성↑

11. DB 규모 확장 : 샤딩 (sharding)

  • 수직 확장은 하드웨어 한계 + SPOF + 비용 급증
  • 샤딩 : 대규모 DB 를 샤드(shard) 라는 작은 단위로 분할
  • 모든 샤드는 같은 스키마를 쓰지만, 데이터는 샤드 간 중복이 없다
  • 예) user_id % 4 → 0, 1, 2, 3번 샤드
  • 보충 이 계산에 쓰는 값이 샤딩 키(파티션 키). 데이터가 고르게 분산되는 키를 고르는 게 가장 중요

샤딩이 만드는 새 문제

문제설명
재샤딩한 샤드가 가득 차거나 데이터가 고르지 않게 쌓이면 샤딩 키를 바꿔 다시 나눠야 한다 (→ 안정 해시, 5장)
유명인사 (핫스팟 키)특정 샤드에 질의가 몰린다. 유명인 계정마다 샤드를 따로 주거나 더 잘게 쪼갠다
조인과 비정규화여러 샤드에 걸친 조인이 어렵다 → DB 를 비정규화해서 한 테이블에서 질의 가능하게 한다

12. 1장 정리

  1. 웹 계층은 무상태로
  2. 모든 계층에 다중화
  3. 가능한 많은 데이터를 캐시
  4. 여러 데이터 센터 지원
  5. 정적 콘텐츠는 CDN
  6. 데이터 계층은 샤딩으로 확장
  7. 각 계층은 독립적 서비스로 분할
  8. 지속적으로 모니터링, 자동화 도구 활용

복습 퀴즈 (눌러서 답 확인)

1. 수직적 확장의 가장 큰 한계 두 가지는?

하드웨어 증설에는 한계가 있고, 서버가 한 대라 장애가 나면 전체가 멈추는 SPOF 라는 점. (장애 대비/다중화도 불가)

2. 웹 서버를 무상태로 만들려면 세션 정보는 어디에 둘까?

서버 밖의 공유 저장소 (Redis 같은 캐시, NoSQL). 어느 서버든 같은 세션을 읽을 수 있게 한다.

3. DB 주가 다운되면? 부가 하나뿐일 땐?

부 중 하나가 새 주로 승격. 부가 하나뿐이었다면 그 부가 주가 되고, 새 부를 추가한다. 복제 지연으로 최신 데이터가 빠질 수 있다.

4. 샤딩에서 가장 중요한 선택과 새로 생기는 문제 3가지는?

데이터가 고르게 분산되는 샤딩 키. 문제 : 재샤딩, 유명인사(핫스팟), 조인과 비정규화.

5. 캐시 사용 시 고려할 점 5가지는?

어떤 데이터를 캐시할지 / 만료 정책 / 일관성 / SPOF(다중화) / 제거 정책(LRU 등).

6. 메시지 큐가 독립적 확장에 도움이 되는 이유는?

생산자와 소비자가 큐로만 연결되어 서로의 상태를 몰라도 된다. 큐 길이에 따라 소비자(워커)만 따로 늘리고 줄일 수 있다.

더 공부할 거리 보충

  • 안정 해시 (consistent hashing) → 책 5장
  • CAP 정리 (일관성 / 가용성 / 분할 내성 중 2개만)
  • DB 인덱스와 쿼리 최적화, 커넥션 풀
  • 로드 밸런싱 알고리즘 (라운드 로빈, 최소 연결, IP 해시)
  • 오토스케일링, 컨테이너 (Docker, Kubernetes)
