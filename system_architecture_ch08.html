8장. URL 단축기 설계

TinyURL 같은 서비스. 7장의 유일 ID 생성기가 여기서 쓰인다.
보충 표시는 공부 노트에 없던 내용을 보강한 부분이다.

1. 기본 기능

  1. 주어진 긴 URL 을 훨씬 짧게 단축
  2. URL 리디렉션 : 단축 URL 로 HTTP 요청이 오면 원래 URL 로 안내
  3. 높은 가용성, 규모 확장성, 장애 감내

예) https://www.example.com/q=chatsystem&c=loggedin... → https://tinyurl.com/y7keocwj

개략적 규모 추정 보충값
쓰기 (매일 1억 URL)초당 약 1,160회
읽기 (읽기:쓰기 = 10:1)초당 약 11,600회
10년 운영1억 × 365 × 10 = 3,650억 개
URL 평균 100바이트약 36.5TB

2. API 엔드포인트

용도요청
URL 단축클라이언트가 긴 URL 을 담아 POST /api/v1/data/shorten (본문 longUrl) → 단축 URL 반환
URL 리디렉션단축 URL 로 GET → HTTP 응답으로 원래 URL 로 보냄

리디렉션 응답 : 301 vs 302

코드의미특징
301 Permanent Moved영구 이동. 브라우저가 캐싱이후 요청은 서버로 오지 않음 → 서버 부하를 줄임
302 Found일시적 이동매번 단축 URL 서버를 거침 → 트래픽 분석에 유리

3. URL 단축

단축 URL 이 www.tinyurl.com/{hashValue} 라면, 긴 URL 을 hashValue 로 바꾸는 해시 함수를 찾는 문제다.

요구사항
입력으로 주어지는 긴 URL 이 다른 값이면 해시값도 달라야 한다
계산된 해시값으로 원래 긴 URL 로 복원될 수 있어야 한다

데이터 모델

  • <단축URL, 원래URL> 순서쌍을 관계형 DB 에 저장 (메모리에만 두면 재시작·용량 한계)
  • 테이블 : id, shortURL, longURL

해시 값 길이 보충

  • 사용 문자 [0-9, a-z, A-Z] = 62개
  • 길이를 n 이라 하면 62n >= 3,650억 을 만족하는 최소 n → n = 7 (627 ≈ 3.5조)

방법 1 : 해시 함수 + 충돌 해소

  • 잘 알려진 해시 함수 CRC32, MD5, SHA-1 이용. 결과가 길어서 앞 7글자만 사용 → 충돌 가능
  • 충돌 해소 : DB 에 이미 있으면 미리 정한 문자열을 덧붙여 다시 해시, 충돌이 없을 때까지 반복
  • 매번 DB 조회가 필요 → 블룸 필터로 성능 개선 보충
  • 👍 단축 URL 의 길이가 고정

방법 2 : base62 변환

  • 숫자(유일 ID)를 62진수로 변환. 0~9 → 0~9, a~z → 10~35, A~Z → 36~61
  • 👍 ID 가 유일하므로 충돌이 없다 → 7장 유일 ID 생성기를 사용
  • 👎 단축 URL 길이가 가변적 / ID 가 순차적이라 다음 URL 을 추측할 수 있다 (보안)
구분해시 + 충돌 해소base62 변환
길이고정가변
유일 ID 생성기필요 없음필요 (7장)
충돌가능 → 해소 필요없음

쓰기 흐름 보충

  1. 입력 longURL 이 이미 DB 에 있는지 확인 → 있으면 기존 shortURL 반환
  2. 없으면 유일 ID 생성 → base62 로 shortURL 생성
  3. id, shortURL, longURL 을 DB 에 저장

4. URL 리디렉션 상세 설계 (읽기 경로)

읽기가 쓰기보다 훨씬 많다 → 캐시로 성능을 높인다.

  1. 사용자가 단축 URL 을 클릭
  2. 로드 밸런서가 요청을 웹 서버에 전달
  3. 단축 URL 이 이미 캐시에 있으면 원래 URL 을 바로 꺼내 클라이언트에 전달
  4. 캐시에 없으면 DB 에서 원래 URL 을 꺼낸다. DB 에도 없으면 잘못된 URL
  5. 꺼낸 URL 을 캐시에 넣은 후 사용자에게 반환

5. 추가 논의 보충

  • 처리율 제한 장치 (4장) : 악의적으로 대량의 URL 을 만드는 것을 IP 기준으로 차단
  • 웹 서버 확장 : 무상태라 추가/삭제 쉬움 / DB 확장 : 다중화, 샤딩
  • 데이터 분석 : 클릭 수, 클릭 시점 (302 가 유리)
  • 가용성, 데이터 일관성, 안정성

복습 퀴즈 (눌러서 답 확인)

1. 301 과 302 의 차이와 각각 유리한 경우는?

301 : 영구 이동, 브라우저가 캐싱해서 서버 부하를 줄인다. 302 : 일시적 이동, 매번 서버를 거치므로 클릭 통계/트래픽 분석에 유리.

2. 해시 길이 n 은 어떻게 정하나?

62n 이 필요한 URL 개수(3,650억)보다 커지는 최소 n. 627 ≈ 3.5조이므로 n = 7.

3. 해시 + 충돌 해소와 base62 변환의 차이는?

해시 방식은 길이가 고정이지만 충돌 해소가 필요하다. base62 는 유일 ID 를 진법 변환하므로 충돌이 없지만 길이가 가변이고 다음 URL 을 추측할 수 있다.

4. base62 로 11157 은?

2TX (2×62² + 55×62 + 59, 55 = T, 59 = X)

5. 읽기 경로에서 캐시가 하는 일은?

자주 요청되는 단축 URL 의 원래 URL 을 메모리에 보관해 DB 조회를 줄이고 응답을 빠르게 한다. 읽기가 쓰기의 10배라서 효과가 크다.

6. base62 방식이 7장과 어떻게 연결되나?

base62 로 바꿀 숫자가 7장의 분산 유일 ID 생성기(스노우플레이크 등)에서 나온다.

  • 블룸 필터
  • 진법 변환 (base64, base58)
  • HTTP 리디렉션과 Location 헤더
